# SOLE ATELIER: a secure three-tier application for AWS

A fictional premium sneaker boutique used as a realistic workload for an AWS architecture I am building **by hand in the Console**: a server-rendered storefront, a JSON cart and catalogue API, and a demo checkout backed by a relational database.

> **Status, stated plainly.** The application is **implemented and tested locally on SQLite**. The AWS architecture is **designed and documented, but nothing has been built or verified in AWS yet**; every AWS item below is PLANNED until there is evidence.

![Target AWS architecture (design, not deployed)](architecture.png)

*Target design, not deployed. Source: [docs/diagrams/architecture.svg](docs/diagrams/architecture.svg).*

## Why this project

Most "three-tier on AWS" demos stop at a default page behind a load balancer. A real shop with per-size stock, a cart and orders raises real questions: how does the app reach a private database, who can read its password, what happens when the database is down, and what does a healthy target group actually prove? The products, prices, stock and labels are fictional, and checkout records a **demo** order and takes no payment.

## Frontend and backend

| | Where | What |
|---|---|---|
| **Frontend** | [`frontend/`](frontend/README.md) | Server-rendered: Jinja2 templates, one CSS file, vanilla JavaScript, local fonts and original SVG illustrations. No Node, no bundler, no separate JS app |
| **Backend** | [`backend/`](backend/README.md) | FastAPI: HTML pages, JSON API (catalogue, cart, orders), health checks. SQLAlchemy on SQLite locally and MySQL (RDS) in AWS, chosen by environment variables |

The backend renders the frontend, so there is one process to deploy. Run command: `uvicorn backend.main:create_app --factory`.

## AWS services and status

| Service | Role | Status |
|---|---|---|
| VPC, subnets, route tables, internet gateway | Public, app and database tiers in two AZs | PLANNED |
| Security groups | `alb-sg` to `app-sg` to `db-sg` chain, no SSH | PLANNED |
| Application Load Balancer | Public entry, health check on `/health` | PLANNED |
| EC2 (launch template, Auto Scaling) | Runs FastAPI in private subnets | PLANNED |
| RDS for MySQL | Orders and stock, private, encrypted | PLANNED |
| NAT gateway | Outbound 443 for the private instances | PLANNED |
| Secrets Manager, IAM role, Session Manager | Secrets out of code, least privilege, shell without port 22 | PLANNED |

Not used on purpose: Route 53, HTTPS, WAF, CloudFront, Multi-AZ RDS, infrastructure as code, CI/CD. Design, request flow and trade-offs: [docs/architecture.md](docs/architecture.md).

## Security highlights

Details and the status of each control: [docs/security.md](docs/security.md).

- **Implemented and tested locally:** the server recomputes prices and checks stock (the browser sends ids only), CSRF tokens on every write, parameterised queries, escaped output and a strict CSP, no customer data in logs, safe error messages, atomic stock reservation, idempotent orders, and a production mode that refuses weak secrets or SQLite.
- **Planned (AWS):** private database, security-group chaining, no SSH, IMDSv2, a role limited to two secrets, and an application database user with DML rights only.
- **Known gaps:** HTTP only, no rate limiting or WAF, no secret rotation for the app user, no payment handling (by design).

## Run it locally

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
copy .env.example .env
uvicorn backend.main:create_app --factory --reload     # http://127.0.0.1:8000
```

`requirements.txt` is what a server installs; `requirements-dev.txt` adds `pytest` and `httpx` for tests. More: [docs/local-setup.md](docs/local-setup.md).

## Limitations and next steps

Known limitations: nothing is deployed; single NAT gateway and single-AZ database (an AZ-a failure likely means an outage); HTTP only; per-browser cart; no migrations tool; illustrated images instead of photographs; the EC2 user-data script is an untested draft. Next: build and verify the AWS side with real screenshots, then HTTPS, Multi-AZ, accounts and payments, and only then infrastructure as code. Review and release assessment: [docs/project/QUALITY_REVIEW.md](docs/project/QUALITY_REVIEW.md).

## AWS cleanup

Nothing is deployed, so nothing is billing today. When you build, the **NAT gateway, load balancer, RDS instance, EC2 instances and secrets bill while they exist**. Set a budget first, then tear down in this order: Auto Scaling group, load balancer and target group, NAT gateway (and release its Elastic IP), RDS, secrets, IAM role, security groups, VPC. Details and the next-day billing check: [docs/cost-analysis.md](docs/cost-analysis.md). Prices are deliberately not quoted; look them up on the day.
