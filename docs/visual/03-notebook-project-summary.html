1What it does and why

A working sneaker storefront (catalogue, per-size stock, cart, demo checkout) designed for a three-tier AWS build done by hand in the Console.

Why it matters: a real app makes the AWS questions real: how does it reach a private database, who can read the password, what does a healthy target group prove?

2Architecture and flow

User→IGW→ALB→EC2 FastAPI→RDS MySQL

Public subnets hold the ALB, private subnets the app, isolated subnets the database. A NAT gateway gives the app outbound 443 for Secrets Manager and Session Manager.

6Key concepts in the design

  • A subnet is public because of its route, not its name
  • Security groups reference security groups
  • Liveness vs readiness health checks
  • Atomic UPDATE ... WHERE stock >= n
  • Idempotency key stops double orders
  • Server prices; browser sends ids only

9Likely interview questions

Healthy target = working app?

No. It proves the ALB reached /health. The database, checkout and security need their own tests.

Last pair, two buyers?

One conditional UPDATE wins; the other gets a 409 and rolls back. Tested in sequence, not under load.

What if AZ a fails?

Probably an outage: NAT and RDS sit in AZ a. Accepted for cost and stated openly.

Interview explanation (30 seconds)

I built a sneaker storefront where the server, not the browser, decides prices and stock, and I tested that by breaking it on purpose. I designed it for a private database behind security-group chaining on AWS, but I have not built or verified the AWS side yet, so I report it as planned.
